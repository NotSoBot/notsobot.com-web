# Dashboard API contract

The dashboard (notsobot.com-web) and the new user-facing endpoints (notsobot.api) are built
against this document. Paths are relative to the API root (the site calls them under `/api`).

## Rules for every endpoint here

- **Auth:** a *user* token (the one from the Discord OAuth login, sent as the raw `Authorization` header).
  Application tokens are not needed and these routes act only on the caller's own data.
- **Errors:** the existing `{code, message, status}` body. `401` = bad/expired session, `403` = missing
  permission, `404` = not found / not yours, `400` = validation.
- **Shapes:** reuse the existing `to_dict()` output of the models wherever one exists, so the bot and the
  dashboard see the same objects. New fields are listed explicitly below.
- **Ownership:** a tag is editable only by its owner (`tag.user_id == caller`). Server settings are
  editable only with the Discord permission the matching bot command requires (see the table below).

## Applications

API applications (`Application`, a token for `Authorization: Bot <token>`). Everyone sees their own, can rename and delete
them; creating one and seeing or resetting a token needs API access: the `API_ACCESS` user flag (`flags & 4`), which
owners hand out from `/admin/applications/access` or the user's flags (owners always have it). Without it those routes are `403` `20004`
(`MISSING_ACCESS`). An application's token stops working (`401`) while it has the `DISABLED` flag (`flags & 2`, set by
staff), its owner is blocked, or its owner doesn't have API access, so taking access away pauses every application they
have and giving it back resumes them. `NOTSOBOT` (`flags & 1`) is the bot's own and is database-only.

| Method | Path | Notes |
|---|---|---|
| GET | `/users/@me/applications` | `{can_create, count, limit, items: Application[]}`, newest first. `can_create` is whether the caller has API access, `limit` is `MAX_APPLICATIONS_AMOUNT` (5). `Application` is `{id, name, flags, owner_id, created}` (`created` from the snowflake); the token is never in the list. |
| POST | `/users/@me/applications` | Body `{name}` (3–32 chars, trimmed, newlines become spaces). Needs API access. Over the limit is `400` code `30001` (`MAX_APPLICATIONS`). Returns the application **with `token`**. |
| PATCH | `/users/@me/applications/<application_id>` | Body `{name}`, same rules. Only the caller's own; anything else is `404` code `10001` (`UNKNOWN_APPLICATION`). Returns the application. |
| DELETE | `/users/@me/applications/<application_id>` | `204`. Same ownership rule. |
| GET | `/users/@me/applications/<application_id>/token` | Needs API access. The application with `token`. |
| POST | `/users/@me/applications/<application_id>/token-reset` | Needs API access. New salt, so every older token stops working. Returns the application with the new `token`. |

The older `/applications` routes are still there for the bot and scripts; `POST /applications` uses the same API access check.

## Voices

Voices cloned with the bot's `tts voice create` command (`/tts voice create`). The name and the audio clips a voice is made from can be changed from
the dashboard, and a voice can be deleted there; cloning one stays with the bot's `tts voice create` command. Every clip is kept in the files bucket
(`voice-clips/{voice_id}/{clip_id}.mp3`, never served by the cdn) as the mp3 that was sent to the cloning service, so voices
can be moved to another one. New voices are cloned on fish.audio, ElevenLabs can't make new ones for now (its existing
voices keep working). A fish.audio model's audio can't be changed, so every clip change there makes a new model from the
stored clips and swaps it in. Voices cloned before that get their ElevenLabs samples copied over by the api's
`scripts/backfill_voice_clips.py`, until then they have no clips.

| Method | Path | Notes |
|---|---|---|
| GET | `/users/@me/commands` | Query: `guild_id` (`0` is DMs), `channel_id`, `command_id` (the exact command id or anything under it: `tag` matches `tag` and `tag.show`; spaces count as dots), `limit` (1–100, default 50), `offset` (up to 100000). Returns `{count, total, first_used, items: CommandUse[]}`, newest first, from clickhouse `user_command_uses` (every attempt the bot reported for the caller). `count` matches the filters, `total` and `first_used` (ISO string, `null` if they never used one) ignore them. `CommandUse` is `{command_id, command_name, command_type, guild_id, channel_id, result, timestamp}`: `command_name` is that variant's name from the command list (`null` if it isn't listed anymore), `guild_id` is `null` in DMs, `result` is how it ended (the bot's `CommandResults`: `ran`, `run_error`, `argument_error`, `blocked`, ..., `null` from before it was tracked). Read only. |
| GET | `/users/@me/reminders` | `{count, items: Reminder[]}`, soonest first (capped at `MAX_REMINDER_AMOUNT`, 300). Reminders are still made (and their time changed) with the bot's `reminder` commands. `Reminder` is `{id, content, guild_id, channel_id, message_id, position, is_all_day, timestamp_start, timestamp_end}` (ISO strings; `guild_id` is `null` for DM reminders, `message_id` is the message that created it). The owner and their DM channel are left out. Reminder text is run through the content scanner whenever it's created or changed (bot or dashboard): guideline hits are blocked with `400` code `40030` (`TEXT_BLOCKED_GUIDELINES`) and flagged as `blocked`, human-review ones go through and are flagged as `logged`. If the scanner is down nothing is saved: `SAFETY_SCAN_FAILED` (`60004`). |
| PATCH | `/users/@me/reminders/<reminder_id>` | Body `{content?, move_to_dms?}`, at least one. `content` max 512 (empty is allowed, the reminder just pings), scanned like above. `move_to_dms: true` clears `guild_id`/`channel_id`/`message_id` so it's sent in the owner's DMs (same as the bot's `reminder delete server`); there's no moving it back. Only the caller's own reminders; anything else is `404` code `10007` (`UNKNOWN_REMINDER`). Returns the reminder, and the bot reschedules it. |
| DELETE | `/users/@me/reminders/<reminder_id>` | `204`. Same ownership rule and `404` as the `PATCH`. |
| GET | `/users/@me/entitlements` | `{count, items: Entitlement[]}`, the caller's premium entitlements, newest first (capped at 100), read only. `Entitlement` is `{id, provider, sku_id, premium_type, type, active, deleted, consumed, starts_at, ends_at, created_at, updated_at, guild_id, granted_by}`: `provider` is `discord` (a Discord subscription) or `manual` (premium an owner gave from `/admin/users`; replaced or removed grants are kept with `deleted: true`). `premium_type` is the `UserPremiumTypes` the sku gives (`null` for an unknown sku), `active` is `Entitlement.is_valid` (not deleted or consumed, and inside `starts_at`/`ends_at`). `granted_by` is the staff id for manual ones, `null` otherwise. Discord's raw payload is left out. `PREMIUM_FREE` has no entitlement. |
| GET | `/users/@me/premium/servers` | `{active, items: PremiumServer[], limit, used}`, the servers the caller gave their premium plus perks to (premium server slots), oldest first. `limit` is `null` for owners (no limit). `PremiumServer` is `{server_id, user_id, slots, created, removable_at, guild}`: `slots` is how many of the caller's slots are on it (Plus AI subscribers can stack them, each adds `MAX_SERVER_AI_MESSAGES` NotSoAI messages every 12 hours), `limit` and `used` count slots, not servers: `removable_at` is when it can be taken off (a server is locked in for 24 hours after getting it), `guild` is `{id, name, icon}` from the guild row, `null` for group dms (added with the bot) and guilds the bot never saved. `active` is whether the caller has premium plus right now, the servers only get anything while they do. A guild only gets premium this way, owning it doesn't give it any; group dms also get their owner's. |
| PUT | `/users/@me/premium/servers/<guild_id>` | Gives a guild one of the caller's slots, or stacks another on a guild that already has one when the caller has Plus AI (locked in again for 24 hours); they must be in it (from their Discord guild list, 404 `UNKNOWN_SERVER` otherwise). Needs premium plus (`PREMIUM_REQUIRED`), at most `limit` servers (`MAX_PREMIUM_SERVERS`). Publishes `PREMIUM_SERVERS_UPDATE`. Returns the list like `GET` plus `created` (`false` when it already had one and the caller has no Plus AI to stack). |
| DELETE | `/users/@me/premium/servers/<server_id>` | Takes one of the caller's slots off a guild or group dm (a stacked one keeps the rest), no membership check. 400 `PREMIUM_SERVER_COOLDOWN` with `removable_at` before it's been 24 hours (only while the caller has premium plus), 404 `UNKNOWN_PREMIUM_SERVER` if it doesn't have one. Publishes `PREMIUM_SERVERS_UPDATE`. Returns the list like `GET`. |
| GET | `/users/@me/voices` | `{count, items: Voice[]}`, newest first (capped at 100; non-owners can only have `MAX_VOICE_CLONE_AMOUNT`, or `MAX_VOICE_CLONE_AMOUNT_PREMIUM_PLUS_AI` with Plus AI). `Voice` is `{id, name, platform_type, created, clips}`: `platform_type` is `VoiceCloneTypes` (`0` ElevenLabs, `1` fish.audio), `created` is an ISO string from the snowflake, `clips` is `VoiceClip[]`, oldest first. `VoiceClip` is `{id, name, duration, size, created}`: `name` is what it was uploaded as, `duration` in ms. The cloning service's ids (voice and samples) are left out. |
| PATCH | `/users/@me/voices/<voice_id>` | Body `{name}` (1–128 chars, trimmed, newlines become spaces). Only the caller's own voices; anything else is `404` code `10003` (`UNKNOWN_VOICE`). Returns the voice with its clips. |
| DELETE | `/users/@me/voices/<voice_id>` | `204`. Deletes the voice on its cloning service, then its clips (rows and stored mp3s), then the voice, same as the bot's `tts voice delete`. No premium needed. Same ownership rule and `404` as the `PATCH`. |
| POST | `/users/@me/voices/<voice_id>/transfer` | Body `{platform_type}` (`VoiceCloneTypes`, only `1` fish.audio can take new voices). Clones the voice again on that service from all its stored clips, points the voice there (same id and name, so tags and tts keep working), then deletes it from the old service. No premium needed. Already on that service is `400` `50001` (`INVALID_FORM_BODY`); a service that can't take new voices is `50023` (`VOICE_CLONE_TYPE_NOT_SUPPORTED`); a voice with no stored clips (cloned before they were kept) is `400` code `50043` (`VOICE_HAS_NO_CLIPS`). Rate limited to 1 per 2 seconds. Returns the voice with its clips. |
| POST | `/users/@me/voices/<voice_id>/clips` | Multipart `file` (or a `url` param), audio or video. Converted to mp3, only the first minute is kept, at least `MIN_VOICE_CLONE_DURATION` (2s, `MEDIA_TOO_SHORT` otherwise). Stored, then added to the voice on its cloning service. Needs premium plus (`PREMIUM_REQUIRED`, like the bot's `tts voice sample`), at most `MAX_VOICE_CLIPS` (10) per voice (`30026` `MAX_VOICE_CLIPS` with `limit`). Rate limited to 1 per 2 seconds. Returns the voice with its clips. |
| PUT | `/users/@me/voices/<voice_id>/clips/<clip_id>` | Replaces a clip: same body and rules as the `POST` (minus the limit). The new audio is added first, then the old clip is removed from the cloning service and storage, so the voice never has none; the new clip gets a new id. Unknown clip is `404` code `10028` (`UNKNOWN_VOICE_CLIP`). Returns the voice with its clips. |
| DELETE | `/users/@me/voices/<voice_id>/clips/<clip_id>` | Removes the clip from the voice on its cloning service, then from storage. No premium needed. A voice's last clip can't be deleted: `400` code `50042` (`VOICE_CLIP_LAST`), delete the voice instead. Returns the voice with its clips. |
| GET | `/users/@me/voices/<voice_id>/clips/<clip_id>/audio` | The clip's mp3 (`audio/mpeg`), only with the owner's token (the dashboard fetches it as a blob). |

## Files

Files the bot uploaded to the file host (`nsb.gg`) for the caller, when a result was over Discord's limit or their
`file_upload_threshold` says to always upload. They can only be listed and deleted from the dashboard.

| Method | Path | Notes |
|---|---|---|
| GET | `/users/@me/files` | Query: `query?` (file name or vanity, case-insensitive), `sort_by?` (`newest` default, `oldest`, `largest`, `name`), `offset?`, `limit?` (1–100, default 50). Returns `{count, items: File[], size, total: {count, size}}`, the caller's files only; expired temporary files are left out. `count`/`size` are what the search matched (all files without one), `total` is every file the caller has; sizes are summed per file in bytes, so the same result uploaded twice counts twice. `File` is `File.to_dict()` without `user`, plus `created` (ISO string from the snowflake): `{id, vanity, filename, filename_base, filename_safe, filename_safe_base, metadata: {duration, extension, framecount, height, mimetype, size, width}, temporary, expires_at, urls: {cdn, vanity}, created}`. |
| POST | `/users/@me/files/delete` | Body `{file_ids}` (1–100 ids), the table's bulk delete. Each file is deleted like the single `DELETE`; ids that aren't the caller's, or are already gone, are skipped rather than failing the request. Returns `{deleted}`. |
| DELETE | `/users/@me/files/<file_id>` | `204`. Deletes the file, and its stored object when no other file of the caller's shares it (same as the bot's `DELETE /files/<file_id>`). Someone else's file, or an expired one, is `404` code `10002` (`UNKNOWN_FILE`). |

## Servers

Login requests the `guilds` OAuth scope in addition to `identify`. The API uses the caller's stored
Discord access token (refreshing it when expired) to read their guilds and permissions (one Discord request,
cached per user for 60s), then keeps only guilds the bot is in with a single query on the `bot_guilds` table.
No per-guild Discord requests are made.

`bot_guilds` is kept up to date by the bot (`notsobot.ts/src/listeners/botguilds.ts`) through two bot-only
endpoints:

| Method | Path | Notes |
|---|---|---|
| PUT | `/info/discord/guilds` | `{shard_count, shard_id, guild_ids}`: the shard's full guild list, sent when the shard connects and every 6 hours. Replaces that shard's rows and drops rows from an older shard count. |
| POST | `/info/discord/guilds/changes` | `{shard_count, added: [{guild_id, shard_id, member_count}], removed: [guild_id], pruned: [guild_id]}`: joins/leaves, batched every 5 seconds (last event per guild wins), each also written to clickhouse `bot_guild_events`. `pruned` is guilds READY listed after the bot had already left them (deleted by discord right after, without ever loading): dropped from `bot_guilds` and recorded with `change` 0 instead of as leaves. |

| Method | Path | Notes |
|---|---|---|
| GET | `/users/@me/guilds` | `Array<{id, name, icon, owner, permissions, can_manage}>`. `permissions` is Discord's bitfield as a string; `can_manage` = has `MANAGE_GUILD` or `ADMINISTRATOR` or is owner. If the session lacks the `guilds` scope: `403` with code `DISCORD_OAUTH_SCOPE_MISMATCH` and `metadata.scopes`, so the site can ask the user to log in again. |
| GET | `/users/@me/guilds/<guild_id>` | `Guild.to_dict(everything=True)` (prefixes, rules, loggers, settings) plus `permissions` (string), `owner` (boolean) and `editable: {loggers, prefixes, rules, rules_admin, settings}` booleans for the caller. Rules are `{id, action, added, admin_bypass, category, command, target_id, target_type, user_id, value}` (see [Rules](#server-rules)) and `settings` has `rules_admin_bypass` (default `true`). Caller must be a member (from the Discord guild list). |
| PUT | `/users/@me/guilds/<guild_id>/prefixes` | Body `{prefix}`; same rules as the bot's `PUT /guilds/<id>/prefixes`. |

### Server rules

A rule says who (`target_type`: `guild` (its `target_id` is the server's id), `channel`, `role` or `user`) can use
what (a `command` id, a `category` (`AI`, `AUDIO`, `CONVERSION`, `EFFECTS`, `FUN`, `INFO`, `MODERATION`,
`MUSIC`, `PERSONAL`, `SEARCH`, `SERVER`, `TAGS`, `UTILITY`) or, with neither, every command). The only `action` is `access`,
its `value` is `{allow, message}` (`message`, max 200, is shown to whoever a block rule stops and is dropped on allow
rules). The most specific rule that matches decides: a user beats a role, a role beats a channel (a channel rule
covers its threads and the channels in a category), a channel beats the server, and on the same target a command beats
its category, which beats every command. Every change publishes `GUILD_RULES_UPDATE` with the server's rules.

The server owner and administrators skip the rules by default. With `rules_admin_bypass` (or a rule's own
`admin_bypass`, which wins over it) off they follow them like everyone else, so a server can fully disable a command for
everyone. The bot's `rules` commands always work for them, so they can't lock themselves out.

Edits from the dashboard should publish the same redis update events the bot's
endpoints publish, so the running bot picks them up immediately.

Display data the API doesn't store (channel/role names for rule targets, channel lists for loggers)
is out of scope for v1; the dashboard shows IDs with mentions-style formatting and accepts IDs as input.

## Admin (NotSoBot staff: owners and moderators)

Every route here needs a user token whose user has the `OWNER` (`flags & 1`) or `MODERATOR` (`flags & 2`) flag; anyone
else gets `403`. The dashboard only shows the **Admin** nav group (`/dashboard/admin/tags`, `/dashboard/admin/tags/directory`, `/dashboard/admin/users`,
`/dashboard/admin/flags`, `/dashboard/admin/reports`, `/dashboard/admin/servers`,
`/dashboard/admin/voices`, `/dashboard/admin/applications`) to staff, and `<RequireStaff/>` sends everyone else back to `/dashboard`.

For applications, the bot's own (`NOTSOBOT`) can only be renamed, and only by owners (disabling, resetting or deleting it is `400`); moderators can't touch another staff member's applications (`403`), and only owners can give or take API access.
Moderators can do everything in the panel except edit user profiles (`flags`/`premium_type`), unblock users or servers, see entitlements or who has API access, change or export a server's settings and data (they can still view and block servers, `editable` is all false for them), delete applications (they can disable them) and delete all of a user's tags, and can't block other moderators. Those answer `403` `MISSING_ACCESS` for moderators.

Enums: content flag `status` `0` pending, `1` confirmed, `2` dismissed, `3` reported, `4` unsure (a reviewer couldn't decide; counts as neither confirmed nor dismissed, so it never auto-confirms or lets matching content through). New flags whose media (or text) matches an already confirmed or reported flag (same `sha256`, or `pdq` within 31 bits) are created as `1` confirmed, with `reviewed_by` set to that flag's reviewer and `notes` set to `Auto-confirmed, matches #<id> by sha256|pdq`, and `auto_confirmed_from` set to that flag's id. Setting a status through `PATCH` clears `auto_confirmed_from`. Only confirmed and reported flags with a pdq are compared, through the partial index `content_flags_pdq_confirmed`. `category`: `unsafe`,
`unsafe_child_safety`, `unsafe_nudity`, `review_child_safety`, `review`. `action`: `blocked`, `replaced`,
`logged`, `not_hosted`. Report `type` `0` bug, `1` user, `2` server (`target_id` is the reported user/guild id, `null`
for bugs; message reports have whoever used the command, from the stored command response, and `tag_id` when the
response was a tag's output); report `status` `0` open, `1` resolved, `2` dismissed. Reports come from the bot's `/report`
command, or bug and tag reports from the website (`POST /users/@me/reports`, or `POST /reports/anonymous` when logged out,
which has no `user`); `guild_id` is `null` when it was used in DMs or sent from the website.

The content flags page is **text only**: `source_url` is never loaded, embedded or linked (shown as plain
selectable text at most), and no media from a flag is previewed in any form.

### Admin removal reasons

Every admin route that removes a tag or its files (`DELETE /admin/tags/<tag_id>`, `/admin/tags/directory/<tag_id>`,
`.../assets/<asset_id>`, `.../media/<asset_id>`, `.../thumbnail` and `/admin/users/<user_id>/tags`) takes
`reason` (`copyright` or `rules`; omitted is a plain delete) and `notice` (max 2000, who sent the notice and where it is)
in the query, written to the tag audit log with each removal. `copyright` counts as a strike against the tag's owner.

Uploads record where each file came from: the admin routes' assets (`tag.assets` and the listing's `assets`) have
`provenance: {created, sha256, source_url, uploaded_by}` (plus `requested_by` and `replaces_id` on archived files), all
null on files from before it was recorded; the public listing leaves it out. `POST /admin/tags/directory/<tag_id>/assets`
also takes `owner_requested` (bool, the owner asked for it, kept as `requested_by`) and `replaces_id` (the same tag's
asset this one is a new version of).
